# /dev-block — сделать блок изменения

Блок — раздел `## … {#bN}` в `architecture/TOBE/blocks.md`: задачи, их тесты и проверяемое «Готово, когда». Код пишет агент по брифу; основная сессия готовит бриф и сама проверяет результат. Сама, без агента, — только маленькая доработка (`PROCESS.md`, раздел 1) и маленькое: одна мысль в 1–3 файлах; отходишь от этого — одной строкой решающему до начала. Команды — из корня репо, в Bash; `$S` — папка сессии. Вызов — просьба о коммитах блока. Что решает кто: бриф, отклонения, не меняющие обещанного, мелкие правки, `Сделано:` — Claude; новый механизм без границ, открытый вопрос — стоп; CONFLICT, меняющий обещанное, — решающий.

1. **Прочитать:** всё, что печатает `python architecture/tools/where.py --read dev-block`.

2. **Можно ли начинать:** блок — аргумент `b<N>` или строка «Дальше:» `python architecture/tools/where.py`.
   - `python architecture/tools/where.py --gate approved` — код 0; иначе `/dev-describe`;
   - блоки из `После:` сделаны; все сделаны — `/dev-deliver`; задача вне описания — сначала `/dev-describe дописать`;
   - стою на ветке из `Ветка:` обложки; иначе `git diff --stat HEAD <ветка>`, потом `git switch <ветка>`; без нужды ветки не переключать: живые сервисы подхватывают код;
   - сервисы подняты (`PROJECT.md`, «Команды»); нет — выяснить почему.

   Блок без кода (проверка вживую) — агента нет, шаги 6–10 пропустить; проверка, которой надо ждать, — не блок, а задача бэклога с `CHECK.md`.

3. **Прочитать блок целиком:**
   ```bash
   python architecture/tools/find.py b<N> --tobe
   python architecture/tools/find.py k-<задача> --tobe
   python architecture/tools/find.py t-<тест> --tobe
   python architecture/tools/find.py c-<правка> --tobe     # «было» и «станет» рядом
   ```
   Через Read: `tasks.md` сервиса целиком, копии с правками его задач, решения обложки; задача называет код — открыть его. Получилось, если можно тремя строками сказать, что даёт блок, и назвать каждый пункт «Готово, когда» с тем, чем он будет проверен.

4. **Стоп-проверки:** ничего не решать и «как будет» не править. Сработал пункт — стоп и `/dev-describe дописать: <чего не хватает>`:
   - новый механизм (хранилище, очередь, версии, кэш, повторы) без согласованного списка частей;
   - новое хранилище без ответов: кто пишет, кто и как читает каждый потребитель, как дописывается и что пересчитывается;
   - «уходит» или «выключается» в коде без `Удаляется:` у задачи; выключенный, но оставленный код запрещён;
   - число без основания в правках или в «Готово, когда».

   Блок в двух репо — решить здесь, где общий код появляется первым и кто делает стык.

5. **Ветка свежая** — перед первым блоком и после паузы: `git fetch origin --quiet && git log --oneline HEAD..origin/main | wc -l`. Не ноль — `git merge origin/main`; конфликт в карте — `map.py sync` по копиям. Прежняя ветка уже слита, а появился новый блок — новая `change/<имя-доработки>` от `main`, поле `Ветка:` — на неё.

6. **Разведка под бриф** — только чтение, много чтения — агенту-сборщику «у каждого утверждения `путь:строка`»:
   - какие файлы менять и какие соседние взять образцом; договор соседнего кода: сигнатуры, исключения, что нельзя менять;
   - как гонять тесты сервиса; что требует базы — не запускать; как сервис запущен и что смонтировано, версии пакетов в контейнере;
   - чужие незакоммиченные правки в обоих репо — в «не трогать»; раздел INTERFACE прошлого отчёта; какие данные есть для живой проверки;
   - блок меняет стенд тестов — каждый сервис стенда проходит проверку настроек, пропуска подписаны нужным ключом;
   - блок пишет миграцию — копия живой базы до запуска агента (`PROJECT.md`): контейнер применит её при любом перезапуске;
   - фоновая работа пишет общие данные, а сервис подхватывает код на лету — в бриф запуск за временной настройкой «выключено»; основная сессия в этом же блоке включает работу и убирает настройку. Работа только в своей базе страховки не требует.

   Получилось, если каждый путь существует, а каждая команда проверки взята из кода или выполнена.

7. **Бриф:**
   ```bash
   python architecture/tools/devBrief.py b<N> --out "$S/brief_<изменение>_b<N>.md"
   ```
   Скрипт подставил задачи, тесты и «Готово, когда». Руками, через Edit: угловые скобки, зачем, граница без «и т. п.», закрытый список проверок с ожидаемыми числами и время. Ненужный раздел удалить. Варианты по роду блока — [variants.md](variants.md). Развилка вне стоп-пунктов шага 4: техника, обещанного не меняет — решить в «Границе»; меняет обещанное — `/dev-describe дописать`. Один агент — один бриф, блок в двух репо — два. `python architecture/tools/devBrief.py --check <файл>` — «бриф готов».

8. **Запуск агента** — отдельным сообщением после записи брифа:
   - `git rev-parse HEAD` — записать коммит до блока;
   - `python architecture/tools/devChangelog.py --now "агент на Б<N>, с <время>, обычно <мин>" --next "<что за ним>" --log "Б<N>: агент запущен"`;
   - `Agent(description: "Б<N>: <название>", subagent_type: "general-purpose")`, промт: «Твой бриф — в файле `<путь>`, изменение «<название>». Прочитай его целиком и выполни ровно по нему; в брифе другое изменение — остановись. Ветка `change/<имя>` уже выбрана, не переключай. Дополнения после предыдущего блока: <коммиты, INTERFACE или «нет»>. Последним сообщением верни отчёт в формате из брифа»;
   - решающему одна строка: кто запущен, что делает, сколько обычно идёт, что дальше;
   - монитор хода, инструмент Monitor, `timeout_ms: 1800000`: `PYTHONIOENCODING=utf-8 python .claude/scripts/agent_progress.py <id агента> <репо агента> <коммит до блока> 300 "Б<N>"`. Событие — решающему 2–3 строками по смыслу; живёт до 30 минут — перезапускать; после отчёта — TaskStop.
   - блоки волны и параллельные — [parallel.md](parallel.md).

   Пока агент коммитит в репо, файлы репо и `CHANGELOG.md` не править: правку съест «спрятал — вернул» pre-commit. Писать — только в `$S` и в другой репо.

9. **Пока агент работает:** готовить бриф следующего блока только чтением; следующий блок опирается лишь на договор и не пересекается по папкам — запускать сразу. Долгих живых расчётов в сервисе, который правит агент, не запускать. Идёт вдвое дольше оценки или ушёл за бриф — TaskStop, `git status`, `git log`, узкий бриф с «уже сделано».

10. **Разбор отчёта:**
    - COMPLETED — дальше; PARTIAL — понять причину: мелкое доделать, иначе узкий бриф. Оборвался с незакоммиченным — продолжать того же агента (SendMessage);
    - CONFLICT: не меняет обещанного — решить самой и поправить правку; меняет — вопрос в чате с номером, рекомендация первой, у вариантов цена, ответ — решение в требованиях и на обложке;
    - отклонения — каждое принять с причиной или вернуть, принятое сразу в «как будет»; INTERFACE — в бриф следующего;
    - заметки — у каждой действие: «в описании X, в коде Y» — поправить правку сейчас; «тесты старого поведения ложны» — тест `уходит` или `меняется` и сделать; «так было и раньше» — не довод, если нарушено обещание; «упало до моих правок» — в журнал давним долгом, не расследовать; про запуск и остановку сервиса — действие в этом же блоке.

11. **Дифф:**
    ```bash
    git log --oneline <коммит до блока>..HEAD
    git show --stat --format='%h %s' <хэш>
    python architecture/tools/devDead.py --since <коммит до блока>
    ```
    В коммитах только пути блока, чужих файлов нет, недостижимого 0; другие языки — `PROJECT.md`, «Мёртвый код». Блок удаления — `python architecture/tools/devDead.py --gone <имена> --in <папки>` пусто. Изменился интерфейс, которым пользуются другие, — README пакета обновлён в этом блоке, описания в коде говорят правду.

12. **Линт и тесты:** повторять, только если код поменялся после прогона агента (перенос с конфликтом, свои правки, механическая замена); иначе числа отчёта, поиск удалённого и живая проверка. Перенос `cherry-pick` без правок — код тот же. Повторяешь — те же команды, плюс весь набор сервиса без базы, только командой из `PROJECT.md`; N = было + новые − ушедшие; каждое `skipped` с причиной. Смотреть на числа в строке, а не только на ✓. Весь набор — вывод в файл и сразу имена упавших: обрезка `tail` оставляет только числа; падение не в своих файлах — сверить с `main` в тех же условиях. Маленький блок основной сессии — по частям: тронутый файл сразу, весь набор в фоне; снимок и сигнал соседу его не ждут, коммит ждёт. Тестовую базу не поднимать.

13. **Живое окружение** — по таблице [live-check.md](live-check.md): что изменил блок, что сделать, что считается «получилось», и правила живой проверки. Перезапуск и миграция — только основная сессия, сразу.

14. **«Готово, когда» по пунктам:** у каждого пункта доказательство — команда и число. Нет доказательства — блок не готов: чинить, а не предлагать остановиться. Сам пункт неверен — гипотеза и опыт, правка формулировки в `blocks.md` и строка решающему при показе, не ослаблять молча. Блок нового сервиса — и без такого пункта: образ собран и контейнер стартовал (тесты на компьютере не видят пакета, которого нет в образе); имена настроек и методов в коде — дословно как в описании: у нового сервиса до закрытия фактов нет, и проверка «как будет» расхождения не увидит. Блок дал объект и сценарий, которые человек проходит в браузере, — проверка мышью ([variants.md](variants.md), «Интерфейс»).

15. **Свои правки и «как будет»:**
    - мелкие правки, найденные проверкой, — основная сессия, отдельным коммитом со строкой блока в сообщении;
    - стык двух агентов: общий код сначала в одном репо, второй после, затем тесты второго против нового первого;
    - стык с соседним репо: блок перенесён, живой сервис на нём, и видимое соседу поменялось или его шаг ждёт нашего — сообщение его сессии сразу (`ListAgents`, затем SendMessage): что ведёт себя иначе, пример вызова и ответа, что он может делать;
    - блок исправлений по ревью: тестов не дописывать, упавшие от задуманной правки — удалять; проба ревьюера должна идти через правимый путь кода, не видит правку — сначала понять почему;
    - ссылки `Код:` «как есть» вне правок на новый код не переводить: их переносит закрытие;
    - принятые отклонения и заметки — правкой копий через Edit; новая `открыто` или `предложено` закрывает ворота `approved` до нового «да» — сказать решающему сразу.

16. **«Сделано:»** — список `Код:` из раздела CODE отчёта в `$S/code_b<N>.txt`, строка `<копия>#<якорь или заголовок> → путь:строка · путь:строка`; имена тестов из кода в `$S/tests_b<N>.txt`, строка `t-… = имя`: ровно заголовок теста, без файла.
    ```bash
    python architecture/tools/map.py block-done b<N> --commits "<хэши>" --summary "<тесты с числами>; вживую <что и числа>" --from "$S/code_b<N>.txt" --tests "$S/tests_b<N>.txt"
    ```
    Блок правил файлы уже отмеченных блоков — ещё `--relocate`; остались строки «вручную» — поставить заново `map.py code`. Открыть 2–3 ссылки и сверить. Ответ должен кончаться «проверка «как будет»: 0 ошибок»; разделы без `Код:` — поставить или назвать причину. По `Сделано:` через месяц должно быть понятно, чем доказано «готово». После коммита шага 18 `python architecture/tools/devChangelog.py --now … --next … --log "Б<N> готов: <что получилось>; <коммиты>"`: ✅ у блока и задач команда ставит сама.

17. **Показ решающему** — 3–6 строк по смыслу, без номеров правок и «STATUS»: что теперь работает его словами, как проверено с живым примером и числом, что нашли и поправили, что поменялось в описании (обещанное — было, стало, почему), что дальше. Блок трогал базу — строка «в базе: …». Нужен выбор — вопрос в чате с номером, 2–3 варианта, рекомендация первой, у каждого цена.

18. **Журнал, коммит, дальше.** Что-то пошло не так — запись, заголовок `### Б<N> «<название>» · <дата>`.
    ```bash
    git add architecture/ CHANGELOG.md && git commit -F "$S/msg_b<N>.txt"     # docs(architecture): Б<N> готов, «как будет» по ходу
    ```
    Только свои пути, никогда `-A` и `.`, без `--no-verify`, без push: push — на доставке. Один такой коммит на блок; у первого блока в нём же строка «да» обложки; маленький блок основной сессии — код и карта одним коммитом. После коммита `where.py`: блок ✅. Есть следующий — `/dev-block` сразу, без «продолжать?»; остановиться, только если решающий просил или сработал стоп шага 4. Все сделаны — `/dev-deliver`.

**По ходу всех шагов:** решающий поправил ход, шаг не сработал или чего-то не хватило — запись в `architecture/JOURNAL.md` (вид — `architecture/PROCESS.md`, раздел 10); скилл, документы, шаблоны и скрипты процесса эта сессия не правит: не хватает инструмента — простейший обход во временной папке или вопрос решающему.

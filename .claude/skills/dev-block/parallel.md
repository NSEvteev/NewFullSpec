# /dev-block: волны и параллельные блоки

Зачем: как вести несколько блоков разом. Кто читает: `/dev-block`, шаг 8, когда блоков в волне больше одного. Общие правила — `architecture/PROCESS.md`, 8.4.

- **Волна:** блоки волны запускаются сразу, каждый своим агентом. Живая проверка — основной сессией в основной папке, по очереди, по мере готовности: коммиты блока переносятся в ветку изменения до его проверки. Отчёт решающему — после волны.
- **Рабочая копия:** у каждого агента своя, по разным папкам:
  ```bash
  python architecture/tools/devWorktree.py add b<N> --link <папка интерфейса>/node_modules
  python architecture/tools/devWorktree.py rm b<N>        # снимает ссылки сам: удаление по ссылке стирает зависимости основной папки
  ```
  Копия внутри репо, в `.claude/worktrees/`: у агента нет окон разрешений, а `git status` основной папки и соседней сессии её не видит. В брифе — раздел «Соседи»: каждая команда Bash — `cd <копия> && …`, Read и Edit — только её путями, первая проверка — импорт пакета из копии.
- **id соседей:** первого агента запустить, его id вписать в бриф второго, второму — сообщением первому дать id второго (SendMessage). Договор между блоками — в «как будет». Основная сессия одна правит «как будет» — по копиям писем.
- **Перенос:** коммиты основная сессия переносит в ветку изменения (`git cherry-pick`), живую проверку ведёт в основной папке; затем `devWorktree.py rm` и `git branch -D <ветка блока>`.
- **Живое трогать можно** (решающий разрешил) — первый блок прямо в основной папке, в рабочую копию только второй: двум агентам с коммитами в одной папке нельзя.
- **Пример** (придуманный): Б2 — сервис, Б3 — интерфейс, договор метода в «как будет». Агент Б3 нашёл, что интерфейсу нужен ещё код ответа 409, — написал агенту Б2 и копией основной сессии; она дописала правку `решено по рекомендации`: видимого человеку не меняет; Б2 добавил ответ. Коммиты Б3 — `cherry-pick`, снимки — в основной папке.

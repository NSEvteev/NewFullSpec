# /dev-deliver — ревью, документы, PR, merge

Вызов — просьба довести изменение до `main`: коммиты своих файлов, push ветки, PR и merge отдельно не спрашиваются. Решающего спрашивать в двух местах: что чинить из ревью (шаг 6) и чужие коммиты в ветке (шаг 10); ещё вопрос — только если снимок разошёлся с обещанным (шаг 3) или много краёв в одном механизме (шаг 5). Временное (брифы, тело PR, пробы, снимки) — в `$S`, папке сессии, не в репо. Образцы показа — [templates/show.md](templates/show.md).

1. **Прочитать:** всё, что печатает `python architecture/tools/where.py --read dev-deliver`.

2. **Где мы и с какого шага:**
   ```bash
   python architecture/tools/where.py --gate blocks-done; echo "ворота: $?"
   python architecture/tools/where.py
   python architecture/tools/devMerge.py check
   gh pr list --head <ветка из «Ветка:» обложки> --state all --json number,state,url
   ```
   PR уже `MERGED` — сразу шаг 14, проверки ниже не нужны. Иначе можно начинать: шаг «доставка», ворота открыты, `build.py --check` — код 0 (красно — чинить до ревью), стою на ветке из `Ветка:` обложки (не стою — выяснить по путеводителю почему: не чужая работа — перейти, `PROCESS.md`, раздел 9; чужая — спросить), сервисы здоровы, неотправленных в `main` нет (иначе шаг 10, потом сюда). `python architecture/tools/devChangelog.py --now "доставка" --next "закрытие"`. Первое совпадение сверху:

   | Состояние | Начать с |
   |---|---|
   | PR `MERGED` | шаг 14 |
   | PR `CLOSED` без merge | спросить решающего: почему закрыт, открывать ли новый |
   | PR `OPEN`, а `PR:` на обложке нет | из шага 11 только номер на обложку, push, затем 13 |
   | PR `OPEN` | шаг 13; были коммиты после PR (`git log <голова PR>..HEAD`, голова — `gh pr view <N> --json headRefOid`), кроме коммита с номером, — сначала шаг 10 и `git push` |
   | PR нет; блок «Исправления по ревью» сделан, отметки шага 8 в «Ход работы» нет | шаг 8 |
   | PR нет; ревью закончено, документы не правились | шаг 9 |
   | PR нет; ревью и документы закончены | шаг 10 |
   | иначе | шаг 3 |

3. **Глазами — то, что видит человек.** Изменение не меняет страницу или её ответ, или снимок с тем же действием назван в `Сделано:` последнего блока, — пропустить. Снимки — из `$S`, командой из `PROJECT.md`. Сделать ровно то действие, которое меняет изменение, на странице, и прочитать, что именно написано: текст ошибки, пустое место, цифры. Заглушка провайдера — та же, что в «Готово, когда» последнего блока. Живая база — только чтение: действие не записало лишнего. Снимок открыть (Read) и сверить с «как будет» по смыслу слов, а не «не упало». Уточнение слов — правкой копии и сборкой; расхождение, меняющее обещанное, — вопрос решающему: «так и оставить / поправить в этом изменении».

4. **Ревью, первый круг.** Маленькая доработка (`PROCESS.md`, раздел 1) — без ревьюеров: основная сессия сама смотрит свой дифф и идёт к шагу 8.
   ```bash
   git diff --shortstat origin/main...HEAD
   git diff --name-only origin/main...HEAD | cut -d/ -f1-2 | sort | uniq -c
   ```
   - `architecture/` — не код: её проверяет `build.py`. Коммиты в соседних репо — в `Сделано:` блоков.
   - Ветка только удаляет код — ревьюер не нужен: сама проверить поиском, что удалённые имена не зовутся (`devDead.py --gone`), тесты и живые методы; отметка шага 8, затем шаг 9.
   - Области — по одной на репо или крупный сервис, не больше трёх; ветка в несколько сотен строк — одна.
   - Бриф — один файл `$S/brief_review_<изменение>.md`, копия [templates/brief-review.md](templates/brief-review.md): мерило и списки «принято осознанно», «отложено решающим» — из `PROJECT.md` и решений обложки. Списки области — в промте агента: `find.py --list правка <сервис> --tobe`, `--list задача`, `--list тест`; правки файлов процессов — в каждую область, чей сервис стоит в их стрелках.
   - Два и более ревьюера — цена одной строкой решающему. Запуск: `general-purpose`, в фоне, параллельно, только читают; сначала Write брифа, потом отдельным сообщением Agent. Промт: «Прочитай бриф `<путь>` и выполни его; изменение «<название>» — в брифе другое, остановись. Твоя область: <репо; команда диффа; что главное; соседний код — как договор, не ревьюить>».
   - Пока работают — список документов для шага 9. Код не трогать, кроме мелкой правки по прямому слову решающего (одна мысль, 1–3 строки): её сразу, ревьюеру строка сообщением.
   - Замечание без `путь:строка` и сценария — вернуть дописать.

5. **Разбор ответов**, по каждому из «РЕАЛЬНЫЕ»:
   - повторить пробу ревьюера самому, в его условиях, и увидеть ту же строку вывода. Не повторилось — не показывать, пока не понятно почему;
   - второй фильтр «случится ли у нас»: не случай, если замечание нарушает правило, которое система и так держит, описывает ожидаемое поведение или требует условий, которых не бывает (`PROJECT.md`, «Как используется»). Такое — в теоретическое, со строкой «почему у нас не случится»;
   - принятое в описании и отложенное решающим — не замечание;
   - много краевых случаев в одном механизме — вопрос решающему о его границе, а не десяток заплаток;
   - реальное — в 2–3 группы по смыслу, у каждой что будет на деле и пример из нашей системы с числами.

6. **Показ и выбор, что чинить** (решает решающий). Где мы строкой, группы по смыслу, живой пример, что предлагаю и цена; без кодов, номеров правок, имён тестов. AskUserQuestion, один, рекомендация первой: «Всё реальное (рекомендую)» — что войдёт, одним блоком, теоретическое не чиним · «Только <группа>» — что останется и чем грозит · «Ничего, дальше к PR» — чем грозит. Мелочи — строкой «попутно поправлю N мелочей в тех же файлах». Поправка того, что человек видит в интерфейсе, — выбор решающего даже в автономном режиме. Реальных нет — не спрашивать: «реальных проблем нет; теоретических N — не чиню», шаг 8.

7. **Исправления:**
   - меняет обещанное — решение решающего в требования и на обложку, и описание раньше кода;
   - одно маленькое (несколько строк в одном месте) — сама: правка «как будет», код, живая проверка, коммит;
   - набор — код сразу, описание рядом: список шага 5 и выбор шага 6 уже задание, агенты кода (`/dev-block`, по агенту на сервис, в своих рабочих копиях) запускаются сразу. Параллельно `/dev-describe дописать: исправления по ревью — <по смыслу>`: правки, задача в `tasks.md`, блок в конец `blocks.md`; «да» — выбор решающего. Расхождение сводит основная сессия при проверке блока, до `Сделано:`;
   - без новых тестов: проверки, сломанные задуманной правкой, удалять, а не переписывать; доказательство — пробы ревьюера, живая проверка, линт;
   - после блока — снова `/dev-deliver`.

8. **Второй круг и отметка.** Второй круг — только по просьбе решающего: тот же бриф, в «Круге» — коммиты после первого, замечания первого по строке, отложенное; новые замечания только реальные и только в новом коде; разбор как шаг 5. Предел — два круга; новое реальное после второго — решающему и одно исправление. `CHANGELOG.md`, «Ход работы»: круги, группы, что выбрал решающий, что отложено — по ней шаг 2 узнаёт, что ревью было. Пошло не так — запись в журнал.

9. **Документы соседних репо** — после последней правки кода, меняющей описанное. Пишет сессия соседа, основная проверяет.
   - Список = `## После блоков` в `blocks.md` и поиск старых путей, команд, методов по живым документам соседа (`PROJECT.md`). Пуст — сказать строкой, в «Ход работы» «документы соседних репо: править нечего», шаг 10.
   - Сообщение его сессии (`ListAgents`, затем SendMessage) — [templates/neighbor-message.md](templates/neighbor-message.md). Куда записать, решает он. Отчёт просить, только когда меняется договор или пример вызова; мелкая правка — одно сообщение, проверка — по его коммиту в `git log`, без переписки. Живой сессии нет — решающему строкой, то же в «Ход работы», шаг 10.
   - Проверка: `git -C <сосед> show <коммит>`: текст совпадает с «как будет» по смыслу, лишних обещаний нет; каждый пример вызова выполнить раз, только чтение; пример с живыми данными сверить с живым ответом. Расхождение — сообщением соседу, в его файлы самому не писать.
   - Новичок обязательно: один-два агента, которые знают только документы соседа (начать с его `CLAUDE.md`), составляют план задачи из жизни и возвращают пробелы. Пробелы этого изменения — соседу; старые — назвать решающему.
   - «Ход работы»: файлы соседа, его коммит, «проверено» — по этой строке шаг 2 узнаёт, что документы сделаны.

10. **Ветка готова к PR:**
    - свои незакоммиченные файлы — по именам; перед коммитом общего файла `git diff <файл>`; чужое и локальные настройки не трогать, файл с чужой незакоммиченной работой не коммитить;
    - линт и тесты пакетов, которые изменила ветка, командами из `PROJECT.md`, числа — в тело PR; `python architecture/tools/build.py --check` — код 0; красно — чинить в ветке: мелкое сама, крупное блоком;
    - `python architecture/tools/devMerge.py check`: неотправленных 0, в списке только коммиты изменения. Чужие коммиты — стоп, AskUserQuestion: «отправить твои коммиты в `main` отдельно, до PR (рекомендую)» · «ветку перенести без них» (`git rebase --onto origin/main <последний чужой> <ветка>`, риск конфликтов) · «включить в PR» (склеятся, не рекомендую).

11. **PR.** Тело — `$S/pr_body_<изменение>.md`, копия [templates/pr-body.md](templates/pr-body.md), без номеров правок и задач. Заголовок — формат коммита проекта, он станет строкой в `main`; область — сервис, где главное изменение, задето поровну — без области.
    ```bash
    python architecture/tools/devMerge.py pr --title "<заголовок>" --body-file "$S/pr_body_<изменение>.md"
    ```
    Скрипт пушит, создаёт PR и сверяет его коммиты с веткой. Номер — в поле `PR:` обложки под `Ветка:` (`PR: #<N>`; второй PR — через запятую): по нему закрытие возьмёт дифф. Коммит `git add architecture/TOBE` — `docs(architecture): номер PR #<N> на обложке`, push. Отдельное ревью PR не делать: дифф тот же; коммиты после последнего круга — `git show --stat` самому.

12. **CI** — как решено в `PROJECT.md`, «CI». Не ждём — свидетельство: местные проверки шага 10, в теле PR — «CI не ждали»; ждём — `gh pr checks <номер> --watch`, красное в том, что ветка трогала, чинить до merge.

13. **Merge и `main` без переключения на старый код:**
    ```bash
    python architecture/tools/devMerge.py merge <N>
    ```
    Вручную `gh pr merge --delete-branch`, `git pull` на `main` и `git switch main` до передвижки нельзя: живой сервис подхватит старый код. Проверка: `MERGED`; `## main...origin/main` без `ahead` и `behind`; пришли чужие более новые коммиты — назвать решающему; сервисы здоровы, изменённые отвечают; `where.py` — шаг «закрытие».

14. **Путеводитель, журнал, итог.** `devChangelog.py --log` по ходу всей доставки: до merge правки идут в ветку с ближайшим коммитом; строка про merge с номером PR — после merge (текст, начинающийся с «/», команда восстанавливает сама), с первым коммитом закрытия в `main`; закрытие откладывается — отдельным коммитом и push. Журнал — если что-то пошло не так, заголовок `### Доставка: <изменение> · <дата>`. Решающему — итог по образцу. Дальше — `/dev-close`.

**По ходу всех шагов:** решающий поправил ход, шаг не сработал или чего-то не хватило — запись в `architecture/JOURNAL.md` (вид — `architecture/PROCESS.md`, раздел 10); скилл, документы, шаблоны и скрипты процесса эта сессия не правит: не хватает инструмента — простейший обход во временной папке или вопрос решающему.

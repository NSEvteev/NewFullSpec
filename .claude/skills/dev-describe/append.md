# /dev-describe: режим «дописать»

Зачем: новый объём после «да». Когда: исправления по ревью, мёртвый код на закрытии, новый сервис, хвосты, которые чинятся одним блоком в сервисах этого изменения: их предлагать дописать сюда, а не «отдельным изменением». Кто читает: `/dev-describe дописать: <что добавить>`. Номера шагов — `SKILL.md`.

1. Границы — до кода, вопросом. Ответ — решение в требованиях и строкой на обложке (шаг 6).
2. Новые правки — в копии (новые копии — `map.py tobe`), задачи и тесты — в `tasks.md`; готовые задачи и блоки не переписывать.
3. Новый блок — в конец `blocks.md`, `После:` — последний блок; «Готово, когда» — по `blocks-rules.md`.
4. Шаги 12, 14, 15; новички — только по новому блоку; посреди кода живая проверка задетых сервисов ругается на «как есть» — это ожидаемо до закрытия.
5. Короткий показ: что добавили, почему, какой блок, «да?». Правка `открыто` или `предложено` закрыла ворота `approved` — после «да» второе «да» дописывается в то же поле: `… ; <дата> · <коммит> · «<слова>»`.
6. Исправления по ревью с готовым списком (что, где, проба ревьюера; выбор решающего сделан) — параллельно с агентами кода, а не до них: код запускается сразу после выбора (`/dev-deliver`, шаг 7), описание сводится с кодом при проверке блока.

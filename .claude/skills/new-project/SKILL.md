# /new-project — настроить новый проект из шаблона

Один раз на проект: после него работают `/backlog` и `/dev`. Кода не пишет и сервисов не заводит: первый сервис приходит первым изменением. Команды — из корня репо, в Bash.

1. **Прочитать** `architecture/KIT.md` целиком и вывод:
   ```bash
   python -c "print(1)"
   python architecture/tools/kit.py status
   ```
   Первая команда печатает не `1` — Python не установлен: в Windows `python` бывает заглушкой Microsoft Store (печатает «Python», код 49), и все команды набора молчат без ошибки. Поставить Python и сказать человеку перезапустить Claude Code: хуки зовут тот же `python` и до перезапуска молча не работают. Код 0 у `kit.py status` при свежей настройке — сказать одной строкой и остановиться. Иначе вывод — то, что точно не заполнено; что подогнать под стек, называют шаги 3–6.

2. **Спросить** одним сообщением то, чего нет в аргументе и файлах; сказанное не переспрашивать:
   - имя проекта и что он делает, 1–2 фразы; редкие слова его предметной области;
   - кто решает: имя, как обратиться («Анне»), слово статуса («решено Анной»); что он понимает, как ему объяснять, что раздражает;
   - логин GitHub владельца, часовой пояс, система и оболочка компьютера;
   - стек: язык, сервисы или программа, база, интерфейс, запуск через Docker compose или нет; команды тестов и линта;
   - кто и как пользуется системой, что идёт само, чего при этом не бывает: по этому ревью решает, что чинить;
   - ждать ли CI перед merge;
   - есть ли соседние репо; правила предметной области, которые нельзя нарушать.

   Человек ещё не решил (например, стек) — так и записать, не выдумывать; дальше по шагам — только то, что известно. Выбор из вариантов — вопросы в чате, все сразу, с номерами; ответ — по номерам.

3. **Настройки:**
   ```bash
   python architecture/tools/kit.py init --title "<имя>" --decider "<имя>" --to "<кому>" --status "решено <кем>" --owner <логин> --timezone <пояс> --names "<имя проекта>,<редкие слова>"
   ```
   Записывает `architecture/project/settings.yaml` и `.github/CODEOWNERS`. В `--names` — только редкие слова: обычное слово даст ложные находки в `kit.py check`. Руками в том же файле, по шапкам ключей:
   - `compose` — есть compose; `ui` — есть интерфейс;
   - `units` — единицы числовых данных проекта; `external` — уже известные внешние системы;
   - `secret_files` — только пути, которые будут; `service_names` — служебные методы и переменные своего стека.

4. **`PROJECT.md`:** каждое `<заполнить: …>` заменить ответом. Заготовленный текст рядом, который проекту не подходит (Windows, тесты через `test_limited.py`, снимки без интерфейса, Docker), — поправить или удалить. Заголовки не переименовывать: на них ссылаются скиллы. Сказать нечего — строка «нет» или «появится с первым сервисом». Выдуманных команд не писать.

5. **Стандарт кода** `architecture/standards/code.md`: заполнить «Что проверяется машиной», удалить разделы чужого стека. Своего стека в заготовке нет — раздел только с тем, что назвал человек; остальное дополнится по находкам.

6. **Обвязка:**
   - `README.md` — описание проекта и как его запустить; раздел «Что нужно на компьютере» оставить, поправив;
   - `CLAUDE.md` — разделы «Команды» и «Устройство»;
   - compose есть — в файле compose своё `name: <проект>`: без него имя проекта берётся по папке (`docker`), и `up` и `down` заденут чужие стеки с такой же папкой на компьютере;
   - `Makefile` — без compose цели `dev`, `stop`, `build`, `clean` заменить своими или удалить; `make test` и `make lint` — командами проекта;
   - `.github/workflows/ci.yml` — установка языка, тесты, линт; `.github/dependabot.yml` — пакеты стека; `.gitignore` — что собирает стек; `.env.example`, `.dockerignore` — по стеку;
   - стек не Python: хуки ruff в `.pre-commit-config.yaml` заменить своим линтером; хук с `language: system` требует установки линтера и в задании `pre-commit` файла `ci.yml`. `scripts/test_limited.py` работает только с pytest, `devDead.py` смотрит только Python: своя проверка — в `PROJECT.md`, «Мёртвый код»;
   - `LICENSE` — лицензия шаблона: текст остаётся вместе с набором; нужна другая для своего кода — спросить решающего;
   - скрипт фактов для новой технологии не писать: у сервиса будет `facts: []`, пока часть не понадобится (`architecture/KIT.md`).

7. **Git и GitHub:**
   - `git remote get-url origin`: смотрит на сам шаблон (копия через `git clone`) — спросить и только тогда удалить `.git`, `git init -b main`;
   - `make setup`; нет `make` — `pip install -r architecture/tools/requirements.txt pre-commit pytest`, `pre-commit install`, `pre-commit install --hook-type commit-msg`;
   - `origin` нет — спросить имя и видимость, создать только словом решающего: `gh repo create <имя> --private --source . --remote origin`. Без `origin` ворота `/dev` не откроются: они сверяют `main` с `origin/main`.

8. **Проверить:**
   ```bash
   python architecture/tools/build.py
   python architecture/tools/kit.py status
   python architecture/tools/kit.py check
   python architecture/tools/build.py --check
   python architecture/tools/live.py
   python architecture/tools/backlog.py check
   ```
   Первые команды — код 0, `live.py` — 0 ошибок; не так — чинить здесь. Собирается пустая карта: сервисов 0. `kit.py status` смотрит только настройки, незаполненные места и владельца; подгонку под стек проверить по шагам 4–6.

9. **Коммит и push:** `chore(project): настройка проекта` — в `main`, push в `origin`. Проверка: `python architecture/tools/where.py --gate start` — ворота открыты.

10. **Показать:** что настроено; что записано как «нет» и когда появится; что дальше — `/backlog`, чтобы записать первую задачу, или `/dev <задача словами>`.

**По ходу всех шагов:** шаг не сработал или чего-то не хватило — запись в `architecture/JOURNAL.md` (вид — `architecture/PROCESS.md`, раздел 10); скилл эта сессия не правит.
